# التشغيل الدائم والوصول بدون VPN

هذا الملف يشرح كيف نبقي قاعدة بيانات Supabase نشطة، وكيف نتعامل مع حجب
`github.io` أو `supabase.co` في بعض الشبكات. اقرأه مع `README.md`.

---

## 1. إبقاء قاعدة البيانات نشطة

مشروع Supabase المجاني قد يتوقف مؤقتاً بعد **7 أيام** بلا نشاط كافٍ في قاعدة
البيانات. الطلبات القليلة اليومية من التطبيق عادةً تكفي، لكن لا يمكن ضمان ذلك
بدون مراقبة خارجية.

### ما هو مطبّق الآن

- `.github/workflows/keep-alive.yml` يعمل **كل 6 ساعات** (4 مرات يومياً).
- `.github/workflows/uptime.yml` يفحص الصحة **كل 15 دقيقة**، ويفتح Issue
  بعنوان `incident` عند الفشل ويغلقه تلقائياً بعد التعافي.
- `.github/workflows/daily-backup.yml` ينشئ **نسخة احتياطية يومية** الساعة
  02:23 UTC عبر `/cron/backup`، ويحتفظ بآخر **30** نسخة في Bucket خاص.
- يطلب `GET /functions/v1/api/health?db=1` لتشغيل قاعدة البيانات.
- يطلب `POST /rest/v1/rpc/ping_keepalive` مباشرةً على Supabase.
- يطلب `/cron/dues` بالسر `CRON_SECRET` لإنشاء استحقاق الشهر الحالي
  وإرسال تذكير نهاية الشهر عند الحاجة.
- الجدول `fund_keepalive` يسجّل آخر نبضة، والدالة `public.ping_keepalive()`
  متاحة للمفاتيح العامة `anon`.

> GitHub قد يؤخر المهام المجدولة أو يوقفها بعد فترة خمول طويلة. لذلك يبقى
> المراقب الخارجي المستقل هو الضمان الأفضل، خصوصاً إن كان الصندوق يعمل يومياً.

### ما معنى «UptimeRobot أو cron-job.org كل 5 دقائق على `/health?db=1`»؟

هذه الجملة تعني: **خدمة مجانية خارج شبكتك تفتح رابطاً محدداً من نظامنا كل خمس
دقائق تلقائياً، بلا تدخل منك، وبلا أي برنامج يُثبَّت على جهازك.**

تفصيل الأجزاء:

| الجزء | المعنى |
|---|---|
| **UptimeRobot** | موقع مجاني لمراقبة المواقع. تسجّل فيه مرة واحدة وتضيف «مراقباً» برابط. |
| **cron-job.org** | موقع مجاني آخر يؤدي نفس الوظيفة (جدولة طلبات آلية). يكفي أحدهما. |
| **كل 5 دقائق** | الخدمة ترسل طلباً آلياً 288 مرة يومياً. هذا هو «النشاط» الذي يمنع Supabase من عدّ المشروع خاملاً. |
| **`/health?db=1`** | مسار في الخادم (Edge Function) يفحص أمرين: أن الخادم يعمل، وأن قاعدة البيانات تستجيب فعلاً (`db=1` تطلب فحص القاعدة). |
| **الرابط الكامل** | `https://vhyckuwhuhdyvhxyqdgt.supabase.co/functions/v1/api/health?db=1` |

**لماذا نحتاجه؟** مشروع Supabase المجاني يُوقف مؤقتاً بعد 7 أيام بلا نشاط.
GitHub Actions في المستودع يرسل نبضات أيضاً، لكن GitHub نفسه قد يؤخر المهام
المجدولة أو يوقفها بعد خمول طويل. المراقب الخارجي مستقل عن GitHub، فيبقى يعمل
حتى لو توقفت كل workflows.

**ماذا يستفيد الصندوق؟** أمران:

1. **منع الإيقاف:** كل طلب يوقظ القاعدة ويُسجّل نبضة في `fund_keepalive`.
2. **تنبيه فوري:** إذا توقف الموقع أو القاعدة يصلك بريد إلكتروني، فتعرف قبل أن
   يشتكي أحد المستخدمين.

**هل هو آمن؟** نعم. الرابط لا يحتوي أي كلمة مرور أو مفتاح سري، ولا يعيد أي
بيانات مالية — يعيد فقط حالة `ok` و`db`. لا تضع مفتاح `service_role` في أي
مراقب خارجي، ولا حاجة له أصلاً.

**خطوات الإعداد الفعلية** (5 دقائق، مرة واحدة فقط):

اختر أحد الخيارين:

#### الخيار الأسهل: UptimeRobot

1. أنشئ حساباً مجانياً على <https://uptimerobot.com>.
2. أضف Monitor من نوع **HTTP(s)**.
3. الرابط:
   `https://vhyckuwhuhdyvhxyqdgt.supabase.co/functions/v1/api/health?db=1`
4. الفترة: **5 دقائق**.
5. أضف مراقباً ثانياً لصفحة الويب (رابط Netlify بعد نشره):
   `https://banan-fund.netlify.app/`

#### الخيار البديل: cron-job.org

1. أنشئ حساباً على <https://cron-job.org>.
2. أنشئ Cron Job كل **5 دقائق**.
3. الرابط:
   `https://vhyckuwhuhdyvhxyqdgt.supabase.co/rest/v1/rpc/ping_keepalive`
4. الطريقة: `POST`.
5. أضف Headers:
   - `apikey`: مفتاح `anon` العام.
   - `Authorization`: `Bearer <anon-key>`.
6. Body: `{}`.
7. Content-Type: `application/json`.

> مفتاح `anon` عام ومصمم للاستخدام في المتصفح، لكن لا تنشره في منشور عام.
> لا تستخدم مفتاح `service_role` في أي مراقب خارجي.

### النسخ الاحتياطي اليومي

النسخة اليومية تُنشأ من داخل Edge Function وتُحفظ في Bucket خاص
`fund-backups`، ويُسجّل بياناتها في جدول `fund_backups`. للتحقق:

```powershell
# من واجهة الإدارة: قائمة النسخ
curl "https://vhyckuwhuhdyvhxyqdgt.supabase.co/functions/v1/api/backups" `
  -H "Authorization: Bearer <admin-access-token>"
```

من صفحة **النسخ الاحتياطي** في التطبيق يمكن تنزيل أي نسخة أو استعادتها.
الاستعادة تتطلب كتابة `RESTORE` وتُنشئ نسخة وقائية قبل الاستبدال.

> لا تحذف Bucket `fund-backups` ولا جدول `fund_backups` أثناء التشغيل.
> نزّل نسخة خارجية شهرياً واحتفظ بها على جهاز أو تخزين منفصل.

### الضمان الحقيقي

المراقبة الخارجية تقلل احتمال الإيقاف، لكن **الضمان الوحيد** هو ترقية مشروع
Supabase إلى خطة **Pro** (إلغاء الإيقاف التلقائي). إن كان الصندوق يعتمد على
النظام يومياً، فخطة Pro هي الخيار الآمن.

## 2. الوصول بدون VPN

إذا كانت الصفحة لا تفتح إلا مع VPN، فالمشكلة ليست في التطبيق بل في **حجب مزوّد
الإنترنت للنطاق**. هذا ما ثبت بالفحص على شبكة YemenNet:

| النطاق | النتيجة بدون VPN |
|---|---|
| `github.io` (GitHub Pages) | **محجوب** — لا استجابة |
| `*.workers.dev` (Cloudflare Worker) | **محجوب** — فشل DNS فوري |
| `*.pages.dev` (Cloudflare Pages) | **محجوب** |
| `cdn.statically.io` | **محجوب** |
| `supabase.co` (قاعدة البيانات وAPI) | **يعمل** |
| `netlify.app` | **يعمل** |
| `vercel.app` | يعمل (احتياطي) |
| `web.app` (Firebase) | يعمل (احتياطي) |
| `surge.sh` | يعمل (احتياطي) |

الخلاصة: **قاعدة البيانات وAPI تعمل بدون VPN، والمحجوب هو استضافة الصفحة فقط.**
لذلك الحل هو نقل صفحة الويب إلى نطاق غير محجوب، مع إبقاء Supabase كما هو.

> **ملاحظة مهمة:** لا يمكن استضافة صفحة الويب على نطاق `supabase.co` نفسه.
> منصّة Supabase تعيد كتابة أي رد `text/html` إلى `text/plain` على نطاقات
> المشروع، فتظهر الصفحة كنص خام بدل أن تعمل. هذا قيد في المنصّة وليس خطأً في
> الكود. الحل الوحيد داخل Supabase هو «Custom Domain» المدفوع.

### خطوة التشخيص

من التطبيق أو صفحة الدخول اضغط **فحص الاتصال** (أو افتح
`/#/diagnostics`). الصفحة تختبر استضافة الصفحة، الإنترنت العام، وSupabase/API
وتعرض النتيجة بلغة واضحة.

يمكنك أيضاً فتح الروابط التالية **بدون VPN** من نفس الجهاز والشبكة، وسجّل أيها يفشل:

| الرابط | ماذا يختبر؟ |
|---|---|
| <https://banan-fund.netlify.app/> | استضافة الويب المعتمدة بدون VPN |
| <https://banan-fund.netlify.app/ping.txt> | وصول الشبكة إلى Netlify (يظهر `banan-fund-ok`) |
| <https://vhyckuwhuhdyvhxyqdgt.supabase.co/functions/v1/api/health?db=1> | Supabase / API |
| <https://walid19-89.github.io/banan--alkher2026/> | GitHub Pages (محجوب على YemenNet — للمقارنة) |
| <https://www.google.com> | الإنترنت عموماً |

- **إذا فشل Netlify فقط:** استخدم Vercel أو Firebase Hosting (الملفان
  `vercel.json` و`firebase.json` جاهزان)، ثم أضف الرابط إلى `APP_ORIGINS`.
- **إذا فشل supabase.co فقط:** تحتاج نطاقاً مخصصاً لـ Supabase (خطة Pro) أو
  وسيطاً عكسياً (Reverse Proxy). نسخة الويب وAPK كلاهما سيتأثران.
- **إذا فشل الاثنان:** استخدم نطاقاً مخصصاً للاستضافة ونطاقاً/وسيطاً لـ Supabase.

### الحل المعتمد للويب: Netlify

النسخة العامة التي تعمل بدون VPN:

**<https://banan-fund.netlify.app/>**

- موقع ثابت (Static site) يُنشر من مجلد `dist`.
- إعداداته محفوظة في `netlify.toml` (أمر البناء `npm run build`، مجلد النشر
  `dist`، وإعادة توجيه كل المسارات إلى `index.html`).

- النشر من جهازك:

  ```powershell
  npm run build
  npx netlify-cli deploy --prod --dir=dist
  ```

  أو عبر السكربت الجاهز الذي يستخدم واجهة Netlify مباشرةً:

  - `VITE_SUPABASE_ANON_KEY`
  - `VITE_API_BASE_URL`

- للتحقق: <https://banan-fund.netlify.app/ping.txt> يجب أن يظهر `banan-fund-ok`.
- `APP_ORIGINS` في Edge Function يجب أن يشمل `https://banan-fund.netlify.app`.
  إن أضفت رابطاً جديداً، حدّث السر ثم أعد نشر الدالة:

  ```powershell

  npx supabase functions deploy api --project-ref vhyckuwhuhdyvhxyqdgt --no-verify-jwt
  ```

### حلول بديلة للويب: Vercel أو Firebase أو Surge

كلها تعمل بدون VPN على هذه الشبكة، والملفات جاهزة في المستودع
(`vercel.json`، `firebase.json`، و`netlify.toml`). نفس الفكرة في الجميع:
Build command `npm run build`، Output `dist`، ونفس متغيرات Vite، ثم أضف رابط
الموقع إلى `APP_ORIGINS` وأعد نشر Edge Function.

- **Vercel:** استورد المستودع من GitHub، أو `npx vercel --prod`.
- **Firebase Hosting:** `npm run build` ثم
  `npx firebase-tools deploy --only hosting`.
- **Surge:** `npm run build` ثم `npx surge dist banan-fund.surge.sh`.

### إذا كان supabase.co محجوباً

الخيارات:

1. **Supabase Custom Domain (Pro):** يمنحك نطاقاً مثل
   `api.yourdomain.com` بدلاً من `*.supabase.co`. هذا هو الحل الرسمي والآمن.
2. **Cloudflare Worker كوسيط عكسي:** يمرّر الطلبات إلى Supabase تحت
   `*.workers.dev`. يحتاج إعداداً دقيقاً لـ CORS وWebSocket (Realtime)،
   وأفضل أن يُنفّذ بمراجعة فنية.
3. **VPN/Proxy:** حل مؤقت، لا يُنصح به للتشغيل الدائم.

### بعد تغيير الروابط

1. حدّث أسرار GitHub Actions:
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`
   - `VITE_API_BASE_URL`
   - `VITE_EDGE_REGION`
2. حدّث رابط الويب داخل `.github/workflows/build-apk.yml` (المتغير
   `VITE_PUBLIC_APP_URL`) إذا تغيّر رابط الاستضافة العام.
3. أعد بناء نسخة الويب.
4. أعد بناء APK جديد بنفس keystore حتى يقبل التحديث فوق القديم.
5. اختبر تسجيل الدخول برقم الهاتف والبريد.
6. أبقِ المشروع القديم كنسخة احتياطية حتى تتأكد من كل شيء.

## 3. التحقق السريع بعد أي تغيير

```powershell
# صحة API وقاعدة البيانات
curl "https://vhyckuwhuhdyvhxyqdgt.supabase.co/functions/v1/api/health?db=1"

# نبضة الإبقاء
curl -X POST "https://vhyckuwhuhdyvhxyqdgt.supabase.co/rest/v1/rpc/ping_keepalive" `
  -H "apikey: <anon-key>" `
  -H "Authorization: Bearer <anon-key>" `
  -H "Content-Type: application/json" `
  -d "{}"
```

إذا رجع `ok: true` و`db: true` فالخادم والقاعدة يعملان.
