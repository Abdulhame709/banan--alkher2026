# استعادة نسخة احتياطية — دليل تقني

> **تحذير:** الاستعادة تستبدل البيانات المالية الحالية بمحتوى النسخة. خذ نسخة جديدة
> من الوضع الحالي أولاً، وأوقف العمل على النظام أثناء الاستعادة.

النسخة الاحتياطية ملف JSON يُنزّل من:
**الإعدادات → النسخ الاحتياطية → تنزيل**.

---

## 1. المتطلبات

- Node.js 22.5 أو أحدث.
- ملف `SUPABASE_KEYS.txt` في جذر المشروع (يحتوي Management API token).
- ملف النسخة الاحتياطية `.json`.

---

## 2. تجربة الاستعادة أولاً (Dry Run)

هذه الخطوة تنفّذ كل عمليات الاستعادة ثم **تتراجع** عنها، للتأكد من سلامة الملف
والاتصال دون تغيير البيانات.

```powershell
cd "C:\Users\Elite\Desktop\بنيان"
node scripts/restore-backup.mjs `
  --file "C:\path\to\banan-backup-20261023-220216.json" `
  --dry-run `
  --yes
```

النتيجة المتوقعة:

```
Backup: 2026-10-23T22:02:16.114Z {"fund_settings":1,...}
Mode: DRY RUN (will roll back)
Dry run complete — all changes rolled back.
Server response: []
```

إذا ظهر خطأ، لا تنفّذ الاستعادة الحقيقية. راجع الرسالة وأصلح السبب.

---

## 3. الاستعادة الفعلية

```powershell
node scripts/restore-backup.mjs `
  --file "C:\path\to\banan-backup-20261023-220216.json" `
  --yes
```

النتيجة المتوقعة:

```
Mode: REAL RESTORE (will commit)
Restore committed successfully.
```

---

## 4. ماذا يفعل السكربت؟

1. يقرأ الملف ويتحقق من `format = banan-fund-backup`.
2. يقرأ Management API token من `SUPABASE_KEYS.txt`.
3. يقرأ قائمة مستخدمي `auth.users` الحاليين.
4. يبدأ معاملة واحدة (transaction).
5. يفرّغ الجداول التالية بالترتيب الآمن:
   - `fund_expense_approvals`
   - `fund_expense_requests`
   - `fund_receipts`
   - `fund_subscriptions`
   - `fund_members`
   - `fund_settings`
   - `fund_audit_logs`
   - `sequences`
   - `fund_user_profiles`
6. يعيد إدخال البيانات بالترتيب:
   - الإعدادات
   - الأعضاء
   - ملفات المستخدمين (فقط لمن لديه حساب Auth حالي)
   - الاستحقاقات
   - السندات
   - طلبات الصرف
   - الاعتمادات
   - التسلسلات
   - سجل التدقيق
7. يستبدل `created_by` / `disbursed_by` بقيمة `null` إذا كان المستخدم لم يعد موجوداً.
8. ينفّذ `commit`، أو `rollback` في وضع التجربة.

> السكربت لا يستعيد `fund_notifications` أو `fund_events` أو ملفات Storage. هذه بيانات
> تشغيلية مؤقتة، ويمكن إعادة توليدها.

---

## 5. التحقق بعد الاستعادة

1. سجّل الدخول بحساب المدير.
2. راجع **لوحة التحكم**: الرصيد النقدي، المقبوضات، المصروفات.
3. راجع **الأعضاء** و**الاستحقاقات** و**السندات**.
4. راجع **التقارير** لفترة قبل وبعد تاريخ النسخة.
5. راجع **سجل التدقيق**.
6. خذ نسخة احتياطية جديدة من الوضع المستعاد.

---

## 6. الاستعادة على مشروع Supabase جديد

إذا كنت تنقل النظام إلى مشروع جديد:

1. أنشئ المشروع وطبّق الترحيلات `0001` و`0002` و`0003`.
2. أنشئ مستخدمي Auth (بنفس البريد أو ببريد جديد).
3. عدّل `SUPABASE_KEYS.txt` ليشير إلى المشروع الجديد (أو مرّر
   `SUPABASE_ACCESS_TOKEN` وعدّل رابط المشروع في السكربت).
4. شغّل الاستعادة. ملفات المستخدمين التي لا يقابلها حساب Auth ستُتخطى.
5. أعد ربط الأدوار يدوياً إذا تغيّرت معرفات المستخدمين.

> إذا تغيّرت معرفات `auth.users`، ستحتاج إلى إعادة ربط:
> `fund_user_profiles.user_id`، `fund_expense_requests.created_by`،
> `fund_receipts.created_by`، و`fund_expense_approvals.approver_id`.
> السكربت الحالي يفترض بقاء نفس معرفات Auth.

---

## 7. استعادة يدوية (بدون السكربت)

إذا تعذّر استخدام Management API:

1. افتح **SQL Editor** في لوحة Supabase.
2. نفّذ `begin;`.
3. نفّذ `truncate` للجداول المذكورة أعلاه.
4. أعد الإدخال من الملف باستخدام `insert` (الترتيب نفسه).
5. نفّذ `commit;`.

> لا تستخدم `delete` على `fund_audit_logs`؛ الـ trigger يمنع الحذف. استخدم `truncate`.
